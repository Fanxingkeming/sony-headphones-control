# 索尼耳机 MDR / Tandem 协议参考（v1，WH-1000XM4 实测）

> 本文是从 `sony-protocol-recon.md` 的探索记录里提炼的参考版，只保留可用结论，不写试错过程。
> 所有字节都在 WH-1000XM4（固件 2.5.0）+ Windows 上实测通过，读回或 App 截图验收。
> 探索过程、失败尝试、证据链见 `sony-protocol-recon.md`。

---

## 1. 概述

| 项 | 值 |
|---|---|
| 协议名 | 索尼内部称 **Tandem**，载荷层是 MDR 命令集 |
| 承载 | 蓝牙经典 **RFCOMM**（不是 BLE GATT） |
| 服务 UUID | `96CC203E-5068-46AD-B32D-E316F5E069BA` |
| 实测机型 | WH-1000XM4，固件 2.5.0，协议版本 `01 00 70 00` |
| 表（命名空间） | `0x0C` = Table#1（主），`0x0E` = Table#2（LE Audio、语音向导） |

---

## 2. 连接

```
RFCOMM → SDP 解析 UUID 96CC203E-5068-46AD-B32D-E316F5E069BA → 得到通道号 → connect
```

**不要写死通道号**：同一副耳机在不同系统上解析出的通道可能不同（XM4 在 Windows 上是 9），
`AndreasOlofsson/mdr-protocol` 记录他的 XM3 分别是 9 和 15。必须走 SDP。

**Windows 实现要点（`AF_BTH` + `WSASocketW`）**：

1. `BTH_ADDR` 是**数值**：`AA:BB:CC:DD:EE:01` → `0xAABBCCDDEE01`，不要做字节翻转
2. `connect` 必须**非阻塞 + select**，且 select 可写**不代表成功**，要再查 `SO_ERROR`
3. `port = 0` + Sony UUID 让系统做 SDP；`port = 通道号` 则直连
4. **同一台 PC 只能开一条** RFCOMM 连接（第二条返回 `10048`，`SO_REUSEADDR` 无效）
5. 耳机同时只接受**一个** tandem 客户端：手机 App 连着时，PC 会拿到 `10050`

## 3. 帧格式

```
3E | ESCAPE( type | seq | len(4字节大端) | payload | checksum ) | 3C
```

| 字段 | 长度 | 说明 |
|---|---|---|
| `3E` | 1 | 起始标记 |
| type | 1 | 见第 5 节 |
| seq | 1 | `00`/`01`，见第 4 节 |
| len | **4** | payload 字节数，大端 |
| payload | N | 首字节是命令码 |
| checksum | 1 | `sum(type .. payload 末字节) & 0xFF`，**对转义前的数据**求和 |
| `3C` | 1 | 结束标记 |

### 3.1 转义

载荷里出现 `3C/3D/3E` 时，替换为 `3D` + `原值 & 0xEF`：

| 明文 | 线上 |
|---|---|
| `3C` | `3D 2C` |
| `3D` | `3D 2D` |
| `3E` | `3D 2E` |

**两个常见错误**（都会导致"部分帧解析失败"）：

- 把长度字段当成 2 字节 —— 小载荷时数值恰好相同，一旦超过 255 就错
- 先反转义再算校验和 —— 必须对**转义前**的原始字节求和

## 4. 序号与 ACK

- 非 ACK 帧的 seq 在 `00`/`01` 之间交替
- 收到一帧必须回 ACK：`type=0x01`、空载荷、**seq = 收到帧的 seq 取反**
- **我方 seq 只在收到对方 ACK 后才推进**；未收到 ACK 时应重发**同一 seq**

```
我方 seq=0 → 设备 ACK seq=1 → 推进到 1
我方 seq=1 → 设备 ACK seq=0 → 推进到 0
```

不 ACK 的后果：设备会无限重发同一帧（看起来像死循环），这不是"设备卡死"。

## 5. 帧类型（DataType）

| byte | 枚举 | 说明 |
|---|---|---|
| `0x00` | DATA | |
| `0x01` | **ACK** | |
| `0x02` | DATA_MC_NO1 | |
| `0x07` | DATA_SSH | |
| `0x09` | DATA_ICD | |
| `0x0A` | DATA_EV | |
| **`0x0C`** | **DATA_MDR** | Table#1，绝大多数命令 |
| `0x0D` | DATA_COMMON | |
| **`0x0E`** | **DATA_MDR_NO2** | Table#2，LE Audio、语音向导 |
| `0x10`–`0x1E` | SHOT_* | 同上 +0x10，单发不需 ACK |
| `0x27`/`0x2C`/`0x2D` | LARGE_DATA_* | 大载荷 |
| `0xFF` | UNKNOWN | |

T1 和 T2 是**两套独立的命令空间**，同一个字节值在两张表里含义不同。查功能时两张表都要看。

## 6. 参数寻址约定

索尼把"一组可读写的设置"建模成 `GET_PARAM / RET_PARAM / SET_PARAM / NTFY_PARAM`，
不同功能族的参数编号塞在 payload 的第二个字节。实测有三种形态：

| 族 | 读 | 写 | 响应 |
|---|---|---|---|
| AUDIO | `E6 <param>` | `E8 <param> <b> <val>` | `E7 <param> <b> <val>` |
| SYSTEM | `F6 <sub>` | `F8 <sub> <b> <val>` | `F7 <sub> <b> <val>` |
| GENERAL | `D6 <type>` | `D8 <type> <settingType> <val>` | `D7 <type> <settingType> <val>` |
| EQEBB | `56 01` | `58 01 <preset> 00` | `57 ...` |
| NCASM | `66 02` | `68 02 ...` | `67 02 ...` |

**GENERAL 族的 type 是设备自己报的**：`D0 <type> 0C` 返回该参数的名字（明文 ASCII），
比猜编号可靠得多。XM4 已知：`D1 = TOUCH_PANEL_SETTING`、`D2 = MULTIPOINT_SETTING`，
`D3` 不存在（无响应）。

## 7. 功能速查（全部实测）

### 7.1 只读

| 功能 | 请求 | 响应 | 解析 |
|---|---|---|---|
| 协议版本 | `00 00` | `01 00 70 00` | 版本号 `0x0070` |
| 能力信息 | `02 00` | `03 00 0A 11` + ASCII MAC | |
| 电量 | `10 00` | `11 00 <pct> 00` | 第 3 字节 |
| 固件版本 | `04 02` | `05 02 <len> <ASCII>` | 实测 `2.5.0` |
| 编解码器 | `18 00` | `19 00 <codec>` | 01=SBC 02=AAC 10=LDAC 20=aptX 21=aptX HD |
| 均衡器 | `56 01` | `57 01 <preset> 06 <6 字节>` | 预设 + 6 段增益（值 −10..10 记为 0..20） |

### 7.2 降噪 / 环境声（NCASM，8 字节）

```
写  68 02 <a> <b> <mode> 01 <focus> <level>
读  66 02  ->  67 02 <a> <b> <mode> 01 <focus> <level>
```

| 位置 | 含义 |
|---|---|
| a | `0x00` 关闭处理，`0x11` 开启处理（设备回显规整成 `0x01`） |
| b | 支持风噪降低时 `0x02`，否则 `0x00` |
| mode | `0x00` 环境声、`0x01` 风噪降低、`0x02` 降噪 |
| 固定 `01` | |
| focus | 关注语音：`0x01` 开 / `0x00` 关，**仅环境声下有效** |
| level | 等级 0–20，仅环境声/关闭有意义 |

常见组合：

```
降噪       68 02 11 02 02 01 00 00
环境声 15  68 02 11 02 00 01 00 0F
关闭处理   68 02 00 02 02 01 00 00
风噪降低   68 02 11 02 01 01 00 00
```

**注意**：`focus` 是**粘性**的，切到降噪不会自动清零；复位要先进环境声、发 focus=0、再切回降噪。

### 7.3 其他开关

| 功能 | 读 | 写 |
|---|---|---|
| 触摸面板 | `D6 D1` → `D7 D1 01 <v>` | `D8 D1 01 <v>` |
| 多点连接 | `D6 D2` → `D7 D2 01 <v>` | `D8 D2 01 <v>`，**必须先开告警**（见第 8 节） |
| 智能免摘 | `F6 05` → `F7 05 00 <v>` | `F8 05 01 <v>` |
| 取下暂停 | `F6 03` → `F7 03 00 <v>` | `F8 03 01 <v>` |
| 自动断电 | `F6 04` → `F7 04 01 <c0> <c1>` | `F8 04 01 <c0> <c1>`，**XM4 只有两态**：`10 00` 取下即关、`11 00` 关闭 |
| DSEE Extreme | `E6 02` → `E7 02 00 <v>` | `E8 02 00 <v>`，`00` 关、`01` 自动 |
| 连接质量 | `E6 01` → `E7 01 00 <v>` | `E8 01 00 <v>`，`00` 声音质量优先、`01` 稳定优先 |
| 语音向导 | 无查询命令 | **T2**：`48 01 01 <v>` → `49 01 01 <v>` |

### 7.4 均衡器写入

```
预设  58 01 <preset> 00
      00 关闭 / 10 明亮 / 11 激昂 / 12 柔和 / 13 放松 / 14 人声
      15 高音增强 / 16 低音增强 / 17 语音 / A1 A2 自定义

频段  58 01 FF 06 <bass+10> <b1+10> <b2+10> <b3+10> <b4+10> <b5+10>
      范围 −10..10 → 0..20；写频段后预设自动变 A0（MANUAL）
```

## 8. 告警门控（敏感设置必需）

有些设置（如多点连接）改完会**断开链路重连**，设备不会直接生效，而是先发一条告警等确认。
**不确认就保持原状**，表现和"被拒绝"一模一样（回显旧值、读回不变）。

### 8.1 流程

```
94 01 00          ALERT_SET_STATUS(FIXED_MESSAGE=01, ENABLE=00)   ← 先打开告警
D8 D2 01 <v>      写设置
  <- 99 01 <MT> 01   ALERT_NTFY_PARAM：MT 表示原因，末字节 01 = 需要应答
98 01 <MT> 01     ALERT_SET_PARAM：原样回 MT + 01（接受）
  ← 链路断开，重连后读回才是新值
```

### 8.2 MT 取值（v1）

| MT | 含义 |
|---|---|
| `0x06` | 因切换到多点而断开（开） |
| `0x07` | 因关闭多点而断开（关） |

**判别方法**：收到 `0x99` = 设备已受理、等你确认；没收到 = 真被拒。
不要用回显值判断——两种情况长得一样。

## 9. 验证方法

按可靠性排序，这是本项目踩过最多坑的地方：

| 手段 | 可靠性 | 说明 |
|---|---|---|
| **GET 读回** | ★★★★★ | 改前改后对比参数值，最直接 |
| **手机 App 截图** | ★★★★ | 唯一能确认"用户看到的确实是这个"的依据 |
| 抓包 diff | ★★★ | 操作前后按 cid 做字节差集，定位未知帧 |
| SET 回显 | ★★ | 只代表命令被接收，不代表状态改变 |
| 听感 | ★ | 嘈杂环境下分辨力不足，本项目中多次误判 |

**抓包有个坑**：Android 的 `btsnoop_hci.log` 是**带缓冲**的，`cp` 出来的文件可能几分钟不长字节。
要拿完整数据，先 `svc bluetooth disable/enable` 让日志轮转为 `.last` 再取。

**UI 自动化**：弹窗按钮别用截图目测坐标（会差 70–80 px 点空），用 PIL 找蓝色文字像素聚类定位。

## 10. 已知限制

| 项 | 说明 |
|---|---|
| 自动断电定时档 | XM4 固件 2.5.0 只接受 `10 00`/`11 00`，5/30/60/180 分钟全部被规整掉 |
| 语音向导语言 | 需要把语言包上传到耳机（几十 MB），中途中断有风险，未实现 |
| GENERAL_SETTING3 | XM4 不存在 |
| 多条连接 | Windows 无法对同一设备开第二条 RFCOMM（`10048`） |
| 连接被占用 | 手机 App 连着时 PC 拿到 `10050`，需先在手机上关掉 App 或蓝牙 |
| 通道扫描 | 连续快速试探多个通道会让耳机进入不可达状态，需等一段时间恢复 |

## 12. v2 协议（LinkBuds S / WF-LS900N 实测）

LinkBuds S 走的是 **v2**，帧层与 v1 **完全相同**（第 3、4 节不用改），
但命令字节含义不同，握手也多一步。同一套 `tandem_client` 可直接复用。

### 12.1 如何判断是 v1 还是 v2

`00 00`（INIT）的响应长度：

| 响应长度 | 协议 | 机型 |
|---|---|---|
| 4 字节（如 `01 00 70 00`） | v1 | WH-1000XM2/XM3/XM4、WF-SP800N… |
| **8 字节**（如 `01 00 03 00 00 07 00 00`） | **v2** | LinkBuds S、WF-1000XM4、XM5、CH720N… |

### 12.2 连接：v2 要用 v2 的服务 UUID

LinkBuds S 注册在 **v2 服务 UUID `956C7B26-D49A-4BA8-B03F-B17D393CB6E2`** 下。
用这个 UUID + `port=0` 走 SDP，0.1s 即可解析（`tools/sdp_probe.py` 实测）；
用 v1 的 `96CC203E-…-E069BA` 则解析失败（`10049`）。
XM4 反之，注册在 v1 UUID 下。所以客户端要"先试 v2 UUID，失败再试 v1"——
mos9527 的客户端正是这个顺序（`StartConnection` 里 `{V2, V1}`）。

### 12.3 握手必须多一步 `06 00`

```
00 00  INIT                     -> 8 字节
02 00  GET_CAPABILITY_INFO      -> 03 00 1D 11 "AC:80:..."（带本机 MAC）
06 00  GET_SUPPORT_FUNCTION     -> 07 00 <功能列表>      ← 少了这一步，后面的族全部不响应
```

这一条踩了很久：只发前两步时，`66 xx` 时通时不通，看起来像设备不稳定；
补上 `06 00` 后所有族稳定响应。另外设备**常忽略新会话的第一条 INIT**，要重试 3–5 次。

### 12.4 命令对照（v1 → v2）

| 功能 | v1（XM4） | v2（LinkBuds S） |
|---|---|---|
| 电量 | `10 00` → `11 00 <pct> 00` | `22 <t>` → `23 <t> ...`，`t`：00 整体 / 01 左右 / 02 充电盒 |
| 固件版本 | `04 02` | 未验证（`04 01` 是型号名） |
| 型号名 | 无 | `04 01` → `05 01 <len> <ASCII>` |
| 编解码 | `18 00` → `19 00 <c>` | `12 02` → `13 02 <c>` |
| 降噪 | `66 02` / `68 02` | **`66 17` / `68 17`** |
| 均衡 | `56 01` / `58 01` | `56 00` / `58 00` |

### 12.5 v2 降噪（type 0x17）

```
读  66 17  ->  67 17 <状态> <总开关> <NC模式> <环境声模式> <等级>
写  68 17 <状态> <总开关> <NC模式> <环境声模式> <等级>
```

| 字段 | 取值 |
|---|---|
| 状态 | `00` 渐变中、`01` 已完成（写入用 `01`） |
| 总开关 | `00` 关闭处理、`01` 开启 |
| NC 模式 | `00` 降噪、`01` 环境声 |
| 环境声模式 | `00` 普通、`01` 关注语音 |
| 等级 | 0–20 |

实测（LinkBuds S）：

```
基线            67 17 01 01 01 01 11     环境声 / 关注语音开 / 17
切降噪          68 17 01 01 00 00 11 -> 67 17 01 01 00 01 11
切环境声        68 17 01 01 01 00 11 -> 67 17 01 01 01 00 11
关闭处理        68 17 01 00 00 00 11 -> 67 17 01 00 00 00 01
```

**注意 `66 30` 不是降噪模式**：type `0x30` 是 `NC_AMB_TOGGLE`，它的载荷字节是
「按键功能」（`Function` 枚举），改它等于改按键分配，不是改模式。我一开始就栽在这上面——
它返回 `67 30 02`，被我误读成"降噪"。

### 12.6 v2 电池：三段

```
22 00  ->  23 00 <pct> 00              整体
22 01  ->  23 01 <L> 00 <R> 00         左 / 右
22 02  ->  23 02 <pct> 00              充电盒
```

### 12.7 v2 的收流要注意

v2 设备会主动推 `A5`（播放状态）和 `A9`（曲目信息，含 UTF-8 中文），
和应答混在同一条流里。按首字节匹配时**不能只看第一条**，要持续接收直到出现期望的命令字，
并给每一帧回 ACK。用 `request()` 那种"发一帧等一帧"的写法会漏掉应答。

工具：`tools/linkbuds.py`

```bash
python tools/linkbuds.py status
python tools/linkbuds.py anc on|off|ambient
python tools/linkbuds.py level 0-20
python tools/linkbuds.py focus on|off
python tools/linkbuds.py eq off|bass|vocal|...
```

### 12.8 设备信息（v2）

```
型号      04 01  ->  05 01 <len> <ASCII>          "LinkBuds S"
固件版本  04 02  ->  05 02 <len> <ASCII>          "2.0.2"
系列颜色  04 03  ->  05 03 <series> <color>       实测 series=0x60 color=0x02
指南信息  04 04  ->  05 04 <5 字节>
```

`DeviceInfoType`：01 型号、02 固件、03 系列与颜色、04 使用指南。
（v2 没有 v1 那种 `04 <type>` 的其他分支，只有这四种。）

**v1 同样实现了这组指令**（2026-11 实测，WH-1000XM4 / 2.5.0）：

```
04 01  ->  05 01 0a "WH-1000XM4"     ~200 ms
04 02  ->  05 02 05 "2.5.0"          ~96 ms
04 03  ->  05 03 30 01               ~98 ms    series=PREMIUM color=BLACK
04 04  ->  05 04 04 30 50 40 60      ~52 ms
```

也就是说 `05 03` 的 `<series>` 字节两代都有（libmdr 的 `ProtocolV1T1.hpp` 同样把
`ModelSeries series` 放在偏移 0x2），**不存在「v1 只有颜色」的 3 字节形式**。
早期文档里的这个假设是错的，已在 `tools/linkbuds.py` 中更正。

`ModelSeries`（取自 libmdr；v2 另有四个取值：0x11 `ULT_POWER_SOUND`、
0x70 `NECKBAND`、0x80 `LINKPOD`、0x90 `GAMING`）：

| 值 | 枚举 | 值 | 枚举 |
|---|---|---|---|
| 0x00 | NO_SERIES | 0x40 | SPORTS |
| 0x10 | EXTRA_BASS | 0x50 | CASUAL |
| 0x20 | HEAR | 0x60 | LINK_BUDS |
| 0x30 | PREMIUM | 0xFF | OUT_OF_RANGE |

`ModelColor`：0x01 BLACK、0x02 WHITE、0x03 SILVER、0x04 RED、0x05 BLUE、
0x06 PINK、0x07 YELLOW、0x08 GREEN、0x09 GRAY、0x0A GOLD、0x0B CREAM、
0x0C ORANGE、0x0D BROWN、0x0E VIOLET；0x11–0x1E 是同一批颜色的 `_I` 变体。

### 12.9 SYSTEM 族：智能对话与按键分配

v2 的 SYSTEM 参数走 `F0`（能力）/ `F2`（状态）/ `F6`（参数）/ `F8`（写参数），
且部分参数还有扩展版本 `FA` / `FC`（EXT_PARAM）。

查到的参数类型与实测可读性：

| type | 含义 | XM4(v1) 对应 | LinkBuds S 实测 |
|---|---|---|---|
| `0x00` | 振动 | — | 无响应 |
| `0x01` | 佩戴播放控制 | 无 | `f7 01 00` 可读，**写入被拒** |
| `0x02` | 智能对话 Type1 | `F6 05` 智能免摘 | **可读写** |
| `0x03` | 按键分配 | 无（v1 是 D1 触摸面板开关） | **可读写** |
| `0x06` | 佩戴检测 | 无 | `f7 06 00 00 00 00 ff ff`（只读状态） |
| `0x0D` | 快捷访问 | 无 | `f7 0d 02 00 00` |
| `0x0E` | 按键分配（受限） | 无 | 与 0x03 同源，回显归一到 0x03 |

**智能对话（Speak-to-Chat）**

```
读  F6 02  ->  f7 02 <类型字节> <0|1>      实测 f7 02 01 01
写  F8 02 01 <0|1>                        实测写入后读回同步
扩展 FA 02 ->  fb 02 <灵敏度> <关注语音> <退出时间>    实测 fb 02 00 01 01
```

注意回显命令字是 `f9 0c ...`（不是 `f9 02`），这是设备侧的正常行为，按首字节匹配即可。

**按键/触摸分配**

```
读  F6 03  ->  f7 03 <len> <preset> <tail>      实测 f7 03 02 35 20
写  F8 03 02 <preset> <tail>                     tail 固定 0x20，不可改
```

`preset` 取值实测（LinkBuds S）：

| 值 | 含义 | 是否被接受 |
|---|---|---|
| `0x10` | 音量控制 | ✅ |
| `0x20` | 播放控制 | ✅ |
| `0x35` | 快捷访问（环境声控制） | ✅ |
| `0xFF` | 无功能 | ✅ |
| 其它（0x00/0x21/0x30/0x31/0x70/0x71…） | — | ❌ 一律被规整为 `0xFF` |

写入 `0x00`（AMBIENT_SOUND_CONTROL）也会被规整成 `0xFF`，说明设备只开放上表这四种。

**一个未解开的结构问题**：按 libmdr 的定义 `presetList` 是 `PodArray<AssignableSettingsPreset>`，
每个元素应有自己的动作列表；但设备返回的只有 `<len> <preset> <tail>` 五个字节里的三个内容字节，
改 `tail` 一律被拒。因此**只实现了改 preset**，没有实现"左右耳分别配置单击/双击/长按"。
App 里能做到后者，说明还有别的入口（很可能是带动作列表的 `F8 03` 变体），未定位。

### 12.10 多点连接（v2）：能读，写入被拒

```
读  D6 D2     ->  d7 d2 00 <val>     实测 01 = 开
写  D8 D2 00 <val>                   ❌ 设备回旧值，不采用
```

试过的组合全部无效：

| 尝试 | 结果 |
|---|---|
| 直接写 `d8 d2 00 00` | 回 `d9 d2 00 01`（旧值） |
| 写 `d8 d2 00 01` | 无回显 |
| 先 `d0 d2 0c`（能力） | 无效 |
| 先 `d2 d2`（GET_STATUS，返回 `d3 d2 00`） | 无效 |
| 先 `94 01 00` 开告警 | 收不到 `99`，写入仍被拒 |
| 用 v1 的 `settingType=01` | 无回显 |

**注意 v2 的 `GsSettingType` 取值与 v1 相反**：

| | BOOLEAN | LIST |
|---|---|---|
| v1（XM4） | `0x01` | `0x02` |
| v2（LinkBuds S） | `0x00` | `0x01` |

所以 v2 的读写都用第三字节 `00`，v1 用 `01`。这一点搞错会全部无响应。

**值语义也与 libmdr 的枚举相反**：libmdr 写 `GsSettingValue{ON=0x00, OFF=0x01}`，
但实测 `01` = 开（与 v1 一致）。**以实测为准。**

结论：多点连接在 v2 上只读。需要在 App 里改。

### 12.11 按键分配（补充）：左右耳可独立设置，但必须先开告警

12.9 里"只能改一个 preset、右耳改不动"的结论**是错的**，已更正。

抓 App 操作（进入页面 → 右耳改成"环境声音控制" → 完成 → 点"确定"）得到的真实流程：

```
F8 03 02 35 35                 预提交：左耳、右耳都设成 0x35
  <- 99 ...                    设备告警：「由于未分配播放控制，因此已禁用语音助手」
98 00 0F 01                    用户点「确定」→ ALERT_SET_PARAM 接受（注意第二字节是 00）
  <- F9 03 02 35 35            提交成功，设备回新值
```

- `F8 03 02 <左> <右>` 的**两个字节分别对应左右耳**，可以独立设置
- 侧别顺序：先左后右（App 界面上 L 在前）
- **必须先发 `94 01 00`（ALERT_SET_STATUS / FIXED_MESSAGE / ENABLE）**，否则写入被静默忽略——回显旧值、读回不变，和"设备不支持"完全一样
- 有副作用的组合（两耳都设成环境声控制 → 播放控制缺失 → 禁用语音助手）会触发设备告警，需要回 `98 00 <MT> 01` 才真正生效；`MT` 取自告警帧第三字节
- v2 的 ALERT_SET_PARAM 是 `98 00 <MT> 01`，**第二字节 00**；XM4(v1) 是 `98 01 <MT> 01`。这一点搞错会答不上

实测（LinkBuds S，每步都读回确认）：

| 操作 | 帧 | 读回 |
|---|---|---|
| 左耳改播放控制 | `F8 03 02 20 20` | `20 20` |
| 左耳改回环境声 | `F8 03 02 35 20` | `35 20` |
| 右耳改音量 | `F8 03 02 35 10` | `35 10` |
| 右耳改回播放 | `F8 03 02 35 20` | `35 20` |

**动作列表不可单独改**。App 的「操作方法」里单击/双击/点击三次/长按四行在控件树中
`clickable=false`（纯展示），内容完全由预设决定：

| 预设 | 单击 | 双击 | 点击三次 | 长按/继续按 |
|---|---|---|---|---|
| `0x35` 环境声音控制/Quick Access | 降噪/环境声音 | 未分配 | 未分配 | 快速注意 |
| `0x20` 播放控制 | 播放/暂停 | 下一首歌 | 上一首歌 | 启动语音助手 |
| `0x10` 音量调节 | 音量 + | — | — | 音量 - |
| `0xFF` 未分配 | — | — | — | — |

所以"自定义触摸动作"这个功能在 LinkBuds S 上不存在，只能选预设。

工具已按此重写：

```bash
python tools/linkbuds.py keys show
python tools/linkbuds.py keys left:playback
python tools/linkbuds.py keys right:quick_ambient
python tools/linkbuds.py keys both:none
```

`set_key()` 内部会自动发 `94 01 00` 并在写入后应答告警。

### 12.12 通知和语音向导（v2 Table#2）与智能对话扩展

**通知和语音向导**（v2 上唯一已知的 T2 命令）：

```
T2  48 01 <val>   ->  49 01 <val>        val: 00 = 开，01 = 关
```

与 v1 的差别：v1 是 `48 01 01 <val>`（4 字节，第三个字节固定 01），
v2 是 **3 字节 `48 01 <val>`**。照 v1 发 4 字节时，设备只回 `49 01 01` 并忽略多余字节，
表现为「发出了但状态不变」，很容易误判成"这功能也在设备端授权里"。

值方向与 libmdr 的 `OnOffSettingValue{ON=0x00, OFF=0x01}` 一致（这次枚举是对的）。

**智能对话扩展**（SYSTEM EXT_PARAM）：

```
读  FA 02  ->  fb 02 <灵敏度> <关注语音> <退出时间>
写  FC 02 <灵敏度> <关注语音> <退出时间>
```

| 字段 | 取值 | 可写 |
|---|---|---|
| 灵敏度 | 00 自动 / 01 高 / 02 低 | ✅ |
| 关注语音 | 实测 01 | ❌ 写 00 被拒 |
| 退出时间 | 00 快 / 01 中 / 02 慢 | ✅ |

回显命令字是 `fd 0c ...`。v2 的 EXT_PARAM 回显统一用 `0x0C` 作为第二字节
（智能对话开关的回显是 `f9 0c`），按「第二字节等于请求第二字节」匹配会全部失配。
